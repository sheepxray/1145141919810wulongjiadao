# 04 · 视觉识别系统

> ⚠️ **性能约束（见 [docs/12](12-帧率与实时性.md)）**：系统要求 **30 FPS** 处理速度。
> 这带来两条**优先于下文其他描述**的硬约束：
> 1. **采集必须用 720p**（5MP 只有 15 fps，硬件上就达不到 30 FPS）；
> 2. **处理前必须降采样，绝不处理全分辨率**。
>
> 30 FPS 的可行性、帧预算与降级阶梯见 [docs/12](12-帧率与实时性.md)。
> 用 `python tools/framerate.py` 复核，用 [`firmware/k230/profiler.py`](https://github.com/sheepxray/1145141919810wulongjiadao/blob/main/firmware/k230/profiler.py) 实测。

## 1. 相机选型

### 1.1 结论

| 相机 | 型号 | 安装 | 任务 |
|---|---|---|---|
| **前视** | OV5640 + 2.8mm | 车头，**俯角 15°** | 搜索棋子（颜色）、近场测墙、障碍 |
| **下视** | OV5640 + 2.8mm | 推板上方，**俯角 60°** | 停车读字、推入段视觉伺服 |

单件约 ¥38，两件 ¥76。

### 1.2 工作模式与分辨率（受 30 FPS 约束）

| 模式 | 相机 | 采集 | 处理分辨率 | 处理帧率 |
|---|---|---|---|---|
| SEARCH | 前视 | 720p scale | 640×360 | **30+** |
| SERVO | 下视 | 720p scale | **320×160 ROI** | **30+** |
| READ | 下视 | 720p | ROI 裁切 | 无要求（静止） |

**核心策略：采集用高帧率（60 fps），处理用低分辨率。**

检测所需像素数（棋子 φ45mm，经验阈值 ≥20px）：

| 分辨率 | 2m 处棋子 | 3m 处棋子 | 结论 |
|---|---|---|---|
| 720p + scale（视场 65.9°） | 22.2px | 14.8px | ✅ 够用 |
| 720p + crop（视场 35.5°） | 45.0px | 30.0px | 更清楚但**看不宽** |

**搜索用 scale 模式**（要的是看宽，不是看清）。

### 1.2 为什么用卷帘快门而不是全局快门

**读字时车是完全静止的**，此时：

- 卷帘快门的**运动错位 = 0**（错位只存在于相机与目标有相对运动的帧）；
- **运动模糊 = 0**（静止时曝光多久都不糊）。

所以全局快门在这个使用方式下**没有收益**，省下 ¥150–300。

> 移动中确实有卷帘错位（0.8m/s 时全画幅约 26mm），但**移动中只做 blob 检测**，
> 而 blob 检测对几 mm 的形状畸变不敏感。错位不影响"这里有个圆形色块"的判断。

### 1.3 ⚠️ 下视相机必须前倾 60°，不能垂直下视

这是 `tools/geometry.py` 暴露的一个设计陷阱。

相机高 150mm 时，**垂直下视（90°）的可见地面区间只有 0–76mm** —— 
画面只覆盖车体正下方，**完全看不到推板前方 100–250mm 处的棋子**。

改为俯角 **60°** 后，可见区间变成 **11–222mm**，覆盖推板开口前方。

| 俯角 | 可见地面区间 | 250mm 处汉字可读性 |
|---|---|---|
| 89°（垂直） | 0 – 76mm | 该距离**不在视场内** |
| 60° | **11 – 222mm** | 径向 113.6px / 横向 160px（舒适） |
| 45° | 52 – 434mm | 舒适，但地面压缩更明显 |

**决策：俯角 60°。**

### 1.4 前视相机的量程限制

俯角 15°、h=150mm、OV5640+2.8mm 时，挡板在 **0.12m 以外全部可见**，
但测距精度随距离恶化：0.5m 处 ±5.2mm，1.0m 处 ±18.5mm，**3m 处 ±154mm**。

**前视相机只用于近场（<1m），全局定位不依赖它。**

## 2. 核心策略：颜色是免费的高价值先验

### 2.1 关键事实

中国象棋：**红方字红、黑方字黑，底色相同。**

所以"这枚棋子是红方还是黑方"是一个**颜色阈值运算**，不需要停车、不需要 CNN。
而策略只需要推**己方颜色**的棋子。

**结果：需要读字的候选立刻减半（32 → 16 枚）。**

### 2.2 分阶段识别流程

```
第一级（移动中，前视相机）：
    颜色阈值 → 连通域 → 棋子候选
    输出：位置 + 颜色（红/黑）
    ↓ 只保留己方颜色
第二级（停车时，下视相机）：
    仅在"己方颜色 + 已在射程内(<400mm)"时触发
    小 CNN → 分值(1-10) + 是否帅/将
```

### 2.3 时间预算（决定"必须选择性读"）

3 分钟 = 180s。单次"停车 → 读字 → 再起步"约 **1.4–1.6s**：

| 阶段 | 耗时 |
|---|---|
| 减速停车 | 0.4s |
| 稳定（等待振动衰减） | 0.3s |
| 采集 + 推理 + UART | 0.3s |
| 加速恢复 | 0.4s |
| **合计** | **约 1.5s** |

| 读字枚数 | 耗时 | 可行性 |
|---|---|---|
| 15 枚 | 22s | ✅ 可接受 |
| 32 枚 | 50s | ❌ 且没时间推棋子 |

**结论：不可能读全部棋子。必须选择性读 —— 而颜色预筛让这个选择几乎免费。**

## 3. 识别算法

### 3.1 棋子检测（经典 CV）

> ⚠️ **性能红线**：以下每一步都必须在**降采样后的图像**上做（640×360），
> 且必须使用 `image` 模块的 C 实现方法。
> **绝不能写 Python 逐像素循环** —— 在 640×360 上就是 23 万次迭代，单帧超 100ms。
> 见 [docs/12](12-帧率与实时性.md) §9。

```python
# ✅ 正确做法：全部是 C 实现
1. img.mean_pooled(2, 2)          # 降采样（合并模式，视场不变）
2. 转 HSV 或用 RGB565 阈值
3. img.find_blobs([红阈值, 黑阈值], pixels_threshold=50, merge=True)
4. 按 b.w()/b.h() 与圆度筛选
5. 输出：质心（图像坐标）+ 颜色
```

```python
# ❌ 这样写帧率必崩（100-1000 倍慢）
for x in range(w):
    for y in range(h):
        if img.get_pixel(x, y) == RED:
            ...
```

**颜色阈值**（需现场标定，见 [docs/09](09-待确认事项与风险.md) R4）：

| 目标 | 阈值方向 |
|---|---|
| 红色字 | R 高、G/B 低 |
| 黑色字 | 亮度低 |

**难点：黑方棋子。** 黑字 + 浅色底，整个棋子看起来是浅色圆盘带黑字。
所以**不能用"黑色区域"直接当棋子**：

| 方案 | 做法 |
|---|---|
| **A（推荐）** | 先检测**棋子圆盘轮廓**（圆形 + 直径符合 φ45 投影），再在盘内统计红色像素占比判红/黑 |
| B | 检测"红字"找红方；对黑方检测深色小区域（字），再向外扩成圆 |

方案 A 更稳：棋子是**浅色圆盘**，与场地对比度通常足够。

### 3.2 字符分类（小 CNN）

| 项目 | 取值 |
|---|---|
| 输入 | 64 × 64 灰度（或 48×48） |
| 类别 | **14 类**（帅/将、仕/士、相/象、俥/車、傌/馬、炮/砲、兵/卒 —— 按红黑分别或合并） |
| 结构 | 3–4 层卷积 + 全局池化 + 全连接（参数量 < 100k） |
| 训练框架 | PyTorch（PC 端） |
| 部署 | **nncase** 量化成 kmodel，跑在 K230 的 KPU |
| 数据集 | 自行采集：不同光照 × 不同角度 × 不同棋子，每类 ≥ 200 张 |

**类别设计建议**：先只分 **7 个"兵种"**（不分红黑，因为颜色已由第一级给出）。
这样类别减半、每类样本翻倍，训练更容易。红黑差异交给颜色通道。

> 即：CNN 只需回答"这枚子是 兵/炮/马/车/象/士/帅 中的哪一个"，不需要回答颜色。

### 3.3 数据集合成（解决样本不足）

真实棋子样本采集费时，可用**合成数据增强**：

1. 拍几张高清棋子照片 → 抠出字形；
2. 用代码随机合成：随机底色、随机光照梯度、随机旋转/缩放/模糊/噪声、
   随机透视变换（模拟俯角压缩）；
3. 生成每类 2000+ 张。

**这是 3 个月时间内最划算的做法** —— 采集成本几乎为零。

## 4. K230 部署

### 4.1 算力评估

| 模型 | K230 KPU 表现 |
|---|---|
| 64×64 的 14 类分类器 | **玩具级任务，轻松** |
| YOLOv5n @ 320×320 | 可实时 |
| ResNet50 / YOLOv8m | 跑不动 |

**算力不是瓶颈，工具链才是。** CanMV/nncase 的模型转换、量化、部署踩坑概率不低。

### 4.2 风险控制策略

**把 nncase 的调试面压到最小**：

| 做法 | 收益 |
|---|---|
| 视觉主线用经典 CV（颜色 + 轮廓） | 大部分功能不依赖 nncase |
| 只把"汉字分类"一个子问题交给 CNN | 出问题时只影响分值识别 |
| 保留**降级策略 B**（不读字，按距离抢枚数） | CNN 完全失败也能参赛 |

### 4.3 部署检查表

- [ ] PC 端训练收敛，验证集准确率 > 95%
- [ ] 导出 ONNX，用 nncase 转 kmodel
- [ ] **量化后重新验证准确率**（量化掉点常被忽略）
- [ ] K230 上单帧推理时间实测 < 50ms
- [ ] 与 STM32 串口联调（docs/11）
- [ ] **光照鲁棒性测试**：在不同色温/亮度下测准确率

## 5. 视觉伺服（第二段推入）

第二段推进必须闭环，否则开环累积误差会吃掉全部容错。

**做法（"车道保持"）**：

```
循环（100 Hz）：
    [下视帧] → 检测目标棋子质心 → 与开口中心比较 → 得到横向偏差 e
    ω_cmd = −Kp · e        （Kp 约 1.5）
    v_cmd = 恒定推进速度
    ↓
    差速运动学分解 → 速度环
```

棋子被保持在开口中心，车沿直线推进。这吸收了：
- 里程计误差；
- 地面摩擦差异导致的直行偏差；
- 中间点 clamp 带来的几何误差。

**这是让方案从"能跑"变成"能得分"的关键一环，不能省。**

## 6. 落位确认

C12 要求棋子**整体**进入球门区。所以推入后必须确认：

| 方法 | 说明 |
|---|---|
| 下视相机回看 | 检测棋子是否还在视野内、位置是否过线 |
| 编码器里程 | 推入后额外前进 120–150mm（过冲量） |
| 堵转信号 | 若推进中撞到墙，说明已到底 |

**推荐组合**：过冲 120–150mm + 下视回看确认。

## 7. 待确认项对视觉的影响

| 待确认项 | 影响 |
|---|---|
| 🔴 **Q2：棋子是否可能背面朝上** | 若可能，**颜色、分值、帅/将全部失效**，整套识别链路作废，必须走降级策略 B |
| Q5：棋子实际直径 | 影响圆形筛选的直径阈值 |
| Q5：刻字方式（阴刻/阳刻/印刷） | 决定字形对比度，影响数据集合成参数 |
| 场地光照条件 | 决定 HSV 阈值，**必须在真实场地标定**，不能在实验室调好就上 |
