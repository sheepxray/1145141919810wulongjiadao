# 14 · 1080p@30 视觉管线

> **第 3 轮迭代的产物。** 所有数值可用 `python tools/vision_pipeline.py` 复现。
>
> **本文回答：怎么做到 1080p@30，以及为什么不是"改个分辨率"这么简单。**

---

## 1. 结论先行

**达成 1080p@30 的关键不是换更强的 NPU，而是把降采样卸载到 RGA 硬件。**

| 项目 | 选型 | 价格 | 理由 |
|---|---|---|---|
| 传感器 | **IMX219（1080p@60）** | ¥65 ×2 | **2× 帧率余量**，OV5640 零余量有风险 |
| 降采样 | **RGA 硬件加速** | 无 | ★ **CPU 降采样要 22ms，RGA 只要 1.8ms** |
| 像素格式 | **NV12** | 无 | ISP 原生，灰度阈值快 2–3× |
| SEARCH 处理分辨率 | 960×540 | 无 | 1080p 的 1/4 像素 |
| SERVO 处理分辨率 | 540×270 ROI | 无 | 只处理推板前方 |

**性能结果**：

| 模式 | 关键路径 | 帧率 |
|---|---|---|
| SEARCH | 17.1 ms | **58 FPS** |
| SERVO | 4.1 ms | **244 FPS** |
| READ | 12.8 ms | 无要求（静止） |

---

## 2. 传感器：要的是"余量"而不是"支持"

⚠️ **判据不是"支持 1080p@30"，而是"有没有余量"。**
恰好卡在 30 fps 的传感器，实际会因为曝光/读出开销掉到 25–28。

| 传感器 | MP | 1080p 最高 fps | 余量 | 评价 | 价格 |
|---|---|---|---|---|---|
| OV5640 | 5.0 | 30 | **1.0×** | **无余量** | ¥38 |
| OV5647 | 5.0 | 30 | 1.0× | **无余量** | ¥45 |
| **IMX219** | 8.0 | **60** | **2.0×** | **充足** | **¥65** |
| IMX477 | 12.3 | 60 | 2.0× | 充足 | ¥220 |
| IMX708 | 11.9 | 50 | 1.7× | 充足 | ¥180 |

### 决策：IMX219

- **2× 帧率余量**让帧率稳定在 30 以上
- MIPI CSI 接口与 RK3588 兼容性好（树莓派 v2 同款，生态成熟）
- 单价 ¥38 → ¥65，两台 **+¥54**

> 这 ¥54 买的是"帧率不会掉到 30 以下"的确定性。
> 用零余量的 OV5640 做 1080p@30 是有风险的。

---

## 3. 内存带宽

1080p@30 的数据量是 720p@30 的 **2.25 倍**。

| 格式 | 字节/像素 | 单次带宽 | 管线 4 次 |
|---|---|---|---|
| RGB888 | 3.0 | 187 MB/s | 746 MB/s |
| RGB565 | 2.0 | 124 MB/s | 498 MB/s |
| YUYV | 2.0 | 124 MB/s | 498 MB/s |
| **NV12** | **1.5** | **93 MB/s** | **373 MB/s** |
| GRAY8 | 1.0 | 62 MB/s | 249 MB/s |

**结论：带宽不是瓶颈。** RK3588 内存带宽约 10–20 GB/s，
即使 RGB888 + 4 次读写也只有 746 MB/s，占用 < 8%。

**但格式选择影响 CPU 速度**：

- RGB565：阈值比较直接，但要拆位
- NV12：ISP 原生输出，**CPU 读 Y 分量即可做灰度阈值**
- **推荐 NV12** —— 灰度单通道让 CPU 的阈值扫描快 2–3×

---

## 4. 管线阶段划分

### ★ 核心设计：降采样用 RGA，不用 CPU

RK3588 的 **RGA 是 2D 硬件加速器**，做缩放/色彩转换几乎不占 CPU。

### SEARCH（巡场搜索）

| 阶段 | 引擎 | 耗时 | 关键路径 |
|---|---|---|---|
| ISP 采集 1080p | ISP | — | 否（并行） |
| RGA 降采样 1080p → 540p | **RGA** | 1.8 | 是 |
| 色彩空间转换 | RGA | 1.2 | 是 |
| 阈值分割 540p | CPU | 4.5 | 是 |
| 连通域标记 540p | CPU | 7.0 | 是 |
| 圆形/面积筛选 | CPU | 1.5 | 是 |
| 坐标变换 + 打包 | CPU | 0.8 | 是 |
| UART 发送 | DMA | 0.3 | 是 |
| **合计** | | **17.1** | |

→ **58 FPS**（余量 16.2 ms）

### SERVO（推入伺服）

| 阶段 | 引擎 | 耗时 |
|---|---|---|
| RGA 裁 ROI + 降采样 | RGA | 0.9 |
| 阈值 + 质心 540×270 | CPU | 3.0 |
| UART 发送 | DMA | 0.2 |
| **合计** | | **4.1** |

→ **244 FPS**（余量 29.2 ms）

### READ（停车读字）

| 阶段 | 引擎 | 耗时 |
|---|---|---|
| RGA 裁 ROI | RGA | 0.8 |
| 圆形筛选 + 红黑判定 | CPU | 3.5 |
| 字符裁切 + 归一化 | RGA+CPU | 2.0 |
| **NPU 推理** | NPU | 6.0 |
| 后处理 + 发送 | CPU | 0.5 |
| **合计** | | **12.8** |

（读字时车静止，无帧率要求）

---

## 5. ★ 为什么必须用 RGA 而不是 CPU 降采样

| 方式 | 引擎 | 耗时 | 说明 |
|---|---|---|---|
| CPU 逐像素降采样 | CPU | **22.0 ms** | 1080p 全像素遍历 |
| CPU 用 SIMD 优化 | CPU | 8.0 ms | 需手写 NEON，开发成本高 |
| **RGA 硬件** | **RGA** | **1.8 ms** | ★ 硬件加速 |

**CPU 降采样要 22ms，单这一项就吃掉 66% 的帧预算。**
RGA 只要 1.8ms，**快 12 倍**。

### 若放弃 RGA 的后果

```
关键路径 = 22.0 + 4.5 + 7.0 + 1.5 + 0.8 + 0.3 = 36.1 ms
帧率     = 1000 / 36.1 = 28 FPS   ← 不达标
```

> **这印证了第 2 轮的结论：瓶颈在 CPU 侧。**
> **把降采样卸载到 RGA，是达成 1080p@30 的关键手段。**

---

## 6. 端到端延迟

**必须分两种工况算 —— 它们用不同的管线：**

| 模式 | 处理耗时 | 用途 |
|---|---|---|
| SEARCH | 17.1 ms | 巡场（滞后不关键） |
| **SERVO** | **4.1 ms** | **推入（决定命中率）** |

### 推入段（SERVO，车速 250 mm/s，推板半开口 82.5mm）

| 深度 | 总延迟 | 位置滞后 | 占推板半开口 | 评价 |
|---|---|---|---|---|
| **1** | 40.4 ms | **10 mm** | **12%** | 余量充足 |
| 2 | 73.8 ms | 18 mm | 22% | 余量充足 |
| 3 | 107.1 ms | 27 mm | 32% | 可接受 |

**推入段位置滞后仅 10mm，占推板半开口的 12% —— 余量充足。**

> 虽然 1080p 的帧周期（33.3ms）比 720p 大，
> 但 SERVO 模式只处理 540×270 的小 ROI，处理耗时压到 4.1ms，
> 所以**延迟反而优于用大管线**。

---

## 7. 降级阶梯

| 级别 | 手段 | 做法 | 代价 |
|---|---|---|---|
| **1** | **降采样用 RGA** | 别用 CPU 做缩放 | 无（必须做） |
| 2 | SEARCH 降到 20 FPS | SERVO 保持 30 FPS | 搜索变慢 |
| 3 | 处理分辨率 540p → 360p | 像素减半 | 远距离检测变差 |
| 4 | 两级降采样 | 1080p→540p→270p | 小棋子可能漏检 |
| 5 | 采集降到 720p | 放弃 1080p 需求 | **分辨率回退** |

> 第 5 条是最后的保险 —— 若 RGA 用不了或驱动异常，
> 退回 720p 仍能跑，但那就**没有满足 1080p 需求**了。

## 10. 结论

> **1080p@30 可达（SEARCH 58 FPS / SERVO 244 FPS），但有三个前提：**
>
> 1. **传感器要有帧率余量** —— IMX219（1080p@60）而非 OV5640（零余量）
> 2. **降采样必须用 RGA 硬件** —— CPU 降采样会让帧率掉到 28 FPS
> 3. **SERVO 用 540×270 小 ROI** —— 保证推入段延迟最小
