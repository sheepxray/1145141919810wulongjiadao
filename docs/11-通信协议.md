# 11 · 通信协议（K230 ↔ STM32）

> 参考实现：`tools/protocol.py`（可直接运行自测）。
> K230 侧是 Python，可直接复用该文件；STM32 侧按本文移植。

---

## 1. 物理层

| 项目 | 取值 |
|---|---|
| 接口 | UART，**921600** 8N1 |
| 方向 | 全双工 |
| 电平 | 3.3V TTL（共地） |
| 校验 | 帧内 CRC16 |
| 心跳 | STM32 每 100ms 发 `HEARTBEAT`，K230 回 `HEARTBEAT_ACK` |

**为什么 921600**：视觉结果帧最大约 200 字节，10Hz 下约 2KB/s。
115200 也够用，但 921600 留足余量（未来加图传/调试信息）。
MCU 侧注意：921600 下 UART 中断频率高，**建议用 DMA + 空闲中断**收帧。

---

## 2. 帧格式

```
┌──────┬──────┬──────┬─────────────┬────────┬──────┐
│ 0xAA │ 0x55 │ LEN  │    PAYLOAD  │ CRC16  │ 0x0D │
│ 1B   │ 1B   │ 1B   │   LEN 字节   │ 2B     │ 1B   │
└──────┴──────┴──────┴─────────────┴────────┴──────┘
```

| 字段 | 长度 | 说明 |
|---|---|---|
| 帧头 | 2B | 固定 `0xAA 0x55` |
| LEN | 1B | PAYLOAD 长度，**0–128** |
| PAYLOAD | LEN B | 见第 3 节 |
| CRC16 | 2B | 小端，覆盖 **LEN + PAYLOAD**（不含帧头和 CRC 自身） |
| 帧尾 | 1B | 固定 `0x0D` |

> **LEN 上限的说明**：字段本身是 u8（可到 255），但协议限制在 **128** 以简化
> MCU 侧的缓冲区分配。实现时曾误设为 64，**自测发现 `TARGET_LIST` 满 8 项时
> 负载为 6 + 8×8 = 70 字节 > 64** —— 即协议上限与自身规范矛盾。
> 现修正为 128，请以此为准（`tools/protocol.py` 的 `MAX_PAYLOAD`）。

### CRC16 参数

| 参数 | 取值 |
|---|---|
| 多项式 | **0x1021**（CRC-16/CCITT-FALSE） |
| 初值 | 0xFFFF |
| 输入反射 | 否 |
| 输出异或 | 0x0000 |
| 校验范围 | `LEN` + `PAYLOAD` |

> 这是最常见的 CCITT-FALSE 变体，网上有大量现成实现，MCU 侧可用表驱动。

### 为什么同时有 CRC 和帧尾

CRC 防数据错误，帧尾防**粘包/半包**后的错误重同步。
两者都保留的成本极低，但能显著降低解析器的复杂度。

## 3. 消息类型

PAYLOAD 第 1 字节是 `MSG_ID`。

### 3.1 K230 → STM32

| MSG_ID | 名称 | 频率 | 说明 |
|---|---|---|---|
| `0x01` | `TARGET_LIST` | 10Hz | 棋子候选列表 |
| `0x02` | `CLASSIFY_RESULT` | 事件 | 停车读字结果 |
| `0x03` | `SERVO_ERROR` | 100Hz | 推入段横向偏差 |
| `0x04` | `HEARTBEAT_ACK` | 10Hz | 心跳应答 |
| `0x05` | `HELLO` | 事件 | K230 启动/重启后上报 |
| `0x06` | `WALL_RANGE` | 20Hz | 近场测墙结果 |

### 3.2 STM32 → K230

| MSG_ID | 名称 | 频率 | 说明 |
|---|---|---|---|
| `0x81` | `HEARTBEAT` | 10Hz | 心跳 |
| `0x82` | `MODE_CMD` | 事件 | 切换 K230 工作模式 |
| `0x83` | `STATE_INFO` | 10Hz | 告知 K230 当前状态机状态与车体运动状态 |
| `0x84` | `PARAM_SET` | 事件 | 下发音视觉参数 |

---

## 4. 负载定义

### 4.1 `TARGET_LIST` (0x01)

| 偏移 | 类型 | 字段 | 说明 |
|---|---|---|---|
| 0 | u8 | msg_id | 0x01 |
| 1 | u8 | count | 候选数量，0–8 |
| 2 | u32 | timestamp_ms | 帧时间戳 |
| 6 | — | entries[] | 每项 8 字节 |

每个 entry（8 字节）：

| 偏移 | 类型 | 字段 | 说明 |
|---|---|---|---|
| 0 | i16 | x_mm | 车体坐标系纵向距离（前为正） |
| 2 | i16 | y_mm | 车体坐标系横向偏移（右为正） |
| 4 | u8 | color | 0=未知 1=红 2=黑 |
| 5 | u8 | conf | 置信度 0–100 |
| 6 | u16 | reserved | 保留（可放面积/圆度） |

**坐标约定**：车体坐标系原点在车体中心，**x 向前（推板方向）、y 向右、z 向上**。

### 4.2 `CLASSIFY_RESULT` (0x02)

| 偏移 | 类型 | 字段 | 说明 |
|---|---|---|---|
| 0 | u8 | msg_id | 0x02 |
| 1 | u8 | piece_class | 0=未识别 1..7=兵种 |
| 2 | u8 | color | 1=红 2=黑 |
| 3 | u8 | score_value | 分值 1–10 |
| 4 | u8 | is_king | 1 表示帅/将 |
| 5 | u8 | conf | 0–100 |
| 6 | i16 | x_mm | 读字时棋子的车体 x |
| 8 | i16 | y_mm | 读字时棋子的车体 y |

**兵种编号**（`piece_class`）：

| 值 | 兵种 | 值 | 兵种 |
|---|---|---|---|
| 1 | 兵/卒 | 5 | 象/相 |
| 2 | 炮 | 6 | 士/仕 |
| 3 | 马 | 7 | **帅/将** |
| 4 | 车 | 0 | 未识别 |

> **颜色与兵种分开编码**：颜色由前视的颜色阈值直接给出（高置信），
> 兵种由 CNN 给出。这样 CNN 只需 7 类，样本量翻倍。

### 4.3 `SERVO_ERROR` (0x03)

推入段视觉伺服，需要低延迟，负载最小化：

| 偏移 | 类型 | 字段 | 说明 |
|---|---|---|---|
| 0 | u8 | msg_id | 0x03 |
| 1 | i16 | err_mm | 棋子相对开口中心的横向偏差 |
| 3 | u8 | valid | 1=检测到棋子 0=丢失 |

**丢失时 `valid=0`**，STM32 应使用上一次有效值并开始减速（避免盲推）。

### 4.4 `WALL_RANGE` (0x06)

| 偏移 | 类型 | 字段 | 说明 |
|---|---|---|---|
| 0 | u8 | msg_id | 0x06 |
| 1 | i16 | front_mm | 前方挡板距离（-1 表示无效） |
| 3 | i16 | left_mm | 左侧距离 |
| 5 | i16 | right_mm | 右侧距离 |
| 7 | u8 | valid_mask | bit0=front bit1=left bit2=right |

### 4.5 `HEARTBEAT` (0x81) / `HEARTBEAT_ACK` (0x04)

| 偏移 | 类型 | 字段 |
|---|---|---|
| 0 | u8 | msg_id |
| 1 | u16 | seq | 递增序号 |

### 4.6 `HELLO` (0x05)

K230 启动或重启后上报：

| 偏移 | 类型 | 字段 |
|---|---|---|
| 0 | u8 | msg_id |
| 1 | u8 | fw_major |
| 2 | u8 | fw_minor |
| 3 | u32 | boot_count |

**STM32 收到 `HELLO` 后必须回送 `STATE_INFO`**，让 K230 重新同步上下文。

### 4.7 `MODE_CMD` (0x82)

| 偏移 | 类型 | 字段 | 说明 |
|---|---|---|---|
| 0 | u8 | msg_id | 0x82 |
| 1 | u8 | mode | 0=IDLE 1=SEARCH 2=CLASSIFY 3=SERVO |

**模式说明**：

| 模式 | K230 行为 |
|---|---|
| IDLE | 只回心跳，不做图像处理（省电、降发热） |
| SEARCH | 用前视相机找棋子，发 `TARGET_LIST` |
| CLASSIFY | 停车读字，发 `CLASSIFY_RESULT` |
| SERVO | 下视伺服，高频发 `SERVO_ERROR` |

**用模式切换而不是让 K230 常开全部处理**，可以显著降低功耗与发热 ——
这对 1.5kg 车体和 K230 的稳定性都有好处。

## 5. 错误处理

### 5.1 K230 侧

| 情况 | 处理 |
|---|---|
| CRC 错误 | 丢弃该帧，`stat.crc_err++` |
| 帧尾错误 | 丢弃，重新搜索帧头 |
| 连续 3 次心跳超时（300ms） | 认为 STM32 失联，进入**安全模式**（停发运动相关消息） |

### 5.2 STM32 侧

| 情况 | 处理 |
|---|---|
| CRC 错误 | 丢弃，计数 |
| **心跳超时 200ms** | 判定 K230 失联 → **进降级策略 B**（[docs/07](07-软件架构与决策策略.md) §5） |
| 收到 `HELLO` | 回送 `STATE_INFO` 重同步 |
| `SERVO_ERROR` 的 `valid=0` 连续 >100ms | 推入段减速停止，避免盲推 |

### 5.3 关键设计原则

> **K230 的失效不能导致整车瘫痪。**

这是硬性要求。STM32 必须是"没有视觉也能跑"的（降级策略 B），
否则 K230 一次重启就可能导致整车停在场地中央。

## 6. 解析器

### 6.1 ⚠️ 不要用"朴素状态机"（一个已发现的真实缺陷）

最初的设计是手写状态机逐字节推进（`WAIT_AA → WAIT_55 → READ_LEN → ...`），
任何一步失败就回到 `WAIT_AA` 重新搜索帧头。

**这个设计有缺陷，并已被 `tools/protocol.py` 的自测实测捕获：**

> 噪声中出现假的 `AA 55` 后，**紧接着的真实帧的帧头会被当成 LEN 字段读走**
> （`0xAA` = 170 > `MAX_PAYLOAD`），于是解析器丢弃整个缓冲区 ——
> 连后面的真实帧一起丢了。
>
> 结果：**一帧噪声之后持续丢包**，而现场噪声是常态。

### 6.2 正确做法：缓冲区 + 重扫描

任何一步校验失败时，**只丢弃当前候选帧头的第一个字节**，
然后从剩余字节里重新搜索 `AA 55`。这样假帧头不会吃掉真帧头。

```python
def _try_parse(self):
    while True:
        idx = self.buf.find(HEAD)
        if idx < 0:
            # 保留最后 1 字节（可能是半个帧头 0xAA）
            if len(self.buf) > 1:
                del self.buf[:-1]
            return None
        if idx > 0:
            del self.buf[:idx]

        if len(self.buf) < 3:
            return None
        length = self.buf[2]
        if length > MAX_PAYLOAD:
            del self.buf[0]          # ★ 只丢一个字节，继续找真帧头
            continue

        frame_len = 2 + 1 + length + 2 + 1
        if len(self.buf) < frame_len:
            return None              # 等待更多字节

        payload = bytes(self.buf[3:3+length])
        crc_rx = self.buf[3+length] | (self.buf[4+length] << 8)
        if crc_rx != crc16(bytes([length]) + payload):
            del self.buf[0]          # ★ 同样只丢一个字节
            continue
        if self.buf[5+length] != TAIL:
            del self.buf[0]
            continue

        raw = bytes(self.buf[:frame_len])
        del self.buf[:frame_len]
        return (payload[0], payload, raw)
```

**关键差异**：失败时 `del self.buf[0]`（丢一个字节）而不是清空缓冲区。

### 6.3 MCU 侧的移植注意事项

| 事项 | 说明 |
|---|---|
| 缓冲区大小 | **≥ 4 × MAX_FRAME**（约 512 字节），避免高负载时溢出 |
| 收帧方式 | **DMA + 空闲中断**（921600 下逐字节中断开销过大） |
| 重扫描成本 | 最坏情况 O(n²)，但 n ≤ 512，MCU 完全可承受 |
| 溢出处理 | 若缓冲区满仍无有效帧，丢弃最旧的一半数据 |

> **这个缺陷值得引以为戒**：朴素的"失败就重置"状态机看起来天经地义，
> 但它和"帧头可能出现在数据中间"这个事实冲突。**必须用自测覆盖"噪声 + 帧头欺骗"场景。**

## 7. 参考实现

`tools/protocol.py` 提供了完整可用的 Python 实现（编码 + 流式解码），
可直接跑自测：

```bash
python tools/protocol.py
```

K230 侧直接 `import protocol` 使用；STM32 侧按本文的帧格式与 CRC 参数移植，
用 DMA + 空闲中断收帧，在主循环里喂给 6.2 节的缓冲区解析器。

自测覆盖：CRC 已知向量、9 种消息的 round-trip、**粘包 / 半包 / 噪声+帧头欺骗**、
payload 位翻转、帧尾错误、超长 payload、LEN 超限。

### 实测带宽（自测脚本输出）

| 消息 | 帧长 | 频率 | 占用 | 占 921600 比例 |
|---|---|---|---|---|
| `TARGET_LIST`（8 项） | 76 B | 10 Hz | 7600 bps | **0.82%** |
| `SERVO_ERROR` | 10 B | 100 Hz | 10000 bps | **1.09%** |

**实测占用仅约 1%** —— 921600 远超需求，余量可用于未来的调试信息或图像特征传输。
若 MCU 侧 DMA 资源紧张，降到 **115200** 也完全够用（占用约 9%）。
